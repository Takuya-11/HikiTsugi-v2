## 1. プロジェクト概要

**プロダクト名**: HikiTsugi v2  
**コンセプト**: 引き継ぐ人は簡単に。引き継がれる人には分かりやすく。

**背景と課題**:
IT運用業務の引き継ぎは属人化しやすく、「書き方がわからない」「フォーマットがバラバラ」「手順が抜ける」「機密情報を外部ツールに入れたくない」という問題が頻発する。既存のHikiTsugi（v1）はlocalStorageのみの非永続データで、共有・複数ドキュメント管理・マルチデバイス対応ができなかった。

**v2の目的**:
- サーバーサイドデータ保存によるマルチデバイス対応
- ログイン認証による作成者管理
- 安全な共有URL機能（閲覧者はログイン不要）
- 複数引き継ぎ書の一元管理

---

## 2. ユーザーロール

| ロール | 認証 | 主な操作 |
|---|---|---|
| **作成者** | ログイン必須 | 引き継ぎ書の作成・編集・削除・共有管理 |
| **閲覧者** | 不要 | 共有URLからの閲覧のみ |

## 3. 機能要件

### FR-01: アカウント管理
- メールアドレス＋パスワードによるアカウント登録
- ログイン・ログアウト
- セッション管理（リフレッシュトークン対応）

### FR-02: ダッシュボード
- 自分が作成した引き継ぎ書の一覧表示
- 表示項目: タイトル・作成日・最終更新日・共有状態（未発行/共有中/停止済み）
- 新規作成ボタン
- 各ドキュメントへのアクセス: 編集・プレビュー・共有管理・削除

### FR-03: 引き継ぎ書の構造（データモデル）

5セクションで構成される:

1. **基本情報**: 業務名・業務概要・引き継ぎ元担当者・引き継ぎ先担当者・業務カテゴリ・実施頻度・作成日
2. **システム・環境情報**: システム名・環境区分・対象機器・OSバージョン・使用ツール・接続情報・参考URL
3. **作業手順**（複数）: 手順名・作業内容・実施タイミング・事前確認事項・操作コマンド・確認方法・中止条件・ロールバック手順・事後確認・注意点・orderフィールド
4. **障害対応**（複数）: 想定される障害・発生時の確認事項・一次対応・復旧確認方法・エスカレーション先・エスカレーション条件・注意点
5. **注意事項・参考資料**: 注意事項・禁止事項・補足事項・参考資料（名前+URL）リスト

### FR-04: 引き継ぎ書の作成・編集
- フォーム入力によるガイデッド作成
- バリデーション（必須項目・URL形式等）
- バリデーションエラー時は該当箇所へスクロール＋フォーカス
- セクションナビゲーション

### FR-05: 作業手順の並び替え
- **【Phase 4確定】上下移動ボタン（↑上へ / ↓下へ）で順序変更**
- orderフィールドを常時保持し、将来のDnD実装に対応できる設計
- 先頭の手順は「上へ」ボタンを無効化、最後尾は「下へ」ボタンを無効化

### FR-06: 自動保存
- **【Phase 4確定】最後の入力から2秒後に自動保存（debounce）**
- 保存状態を3状態で表示:
  - `保存中...` — debounce待機中またはサーバー送信中
  - `保存済` — サーバーへの保存完了
  - `保存失敗` — ネットワークエラー等（ローカルバックアップに保存済みを明示）
- **【Phase 4確定】ネットワーク障害時はローカルバックアップに書き込み**（IndexedDB or localStorageを Phase 5で決定）
- **【Phase 4確定】競合検知**: `updated_at`（またはversionカウンタ）を使って古いデータによる上書きを防止

### FR-07: プレビューと印刷
- 入力内容の印刷用プレビュー表示
- PDF保存・印刷ボタン
- A4縦レイアウトに最適化

### FR-08: 共有URL機能
- 閲覧専用の共有URLをUUID/トークンベースで発行
- 閲覧者はログイン不要でアクセス可能
- **【Phase 4確定】共有URLの停止は手動のみ（MVPに有効期限設定UIは含まない）**
- **【Phase 4確定】DBは将来の有効期限設定に対応できる設計にする**（`expires_at` カラムを用意し、MVPでは `NULL`）
- 停止後に再発行可能（新トークンを発行、旧トークンは無効のまま）

共有トークンの状態:
| 状態 | 説明 |
|---|---|
| 未発行 | URLを発行していない |
| 共有中 | 有効なURLが存在、閲覧可能 |
| 停止済み | 手動停止済み、閲覧不可 |
| 期限切れ（将来） | 有効期限切れ（v1.0以降） |

### FR-09: 閲覧画面
- 共有URLからの読み取り専用表示
- 編集UIは一切表示しない
- PDF保存・印刷ボタン
- アクセスエラー時: 停止済み・無効URLに対応したエラーメッセージ

### FR-10: アクセス制御
- 作成者が作成した引き継ぎ書には、本人以外ログイン済みでもアクセス不可（本人のみ）
- 閲覧画面は共有トークンが有効であればログイン不要でアクセス可
- 無効・停止済みトークンはエラー画面へリダイレクト
- Supabase採用時はRow Level Security（RLS）で制御

### FR-11: エラーハンドリング
- バリデーションエラーは該当フィールドに即時表示
- サーバーエラーはトースト通知（操作を妨げない形式）
- ネットワーク障害は自動保存失敗として通知、ローカルバックアップの存在を明示
- 認証切れは自動的にログイン画面へリダイレクト

## 4. 非機能要件

### NF-01: セキュリティ
- HTTPS必須
- パスワードはハッシュ化して保存（Supabase Auth使用時は自動管理）
- 秘密情報（APIキー・シークレット）をソースコードやGitに含めない
- 環境変数は `.env.local` で管理（Gitignore対象）
- RLSで作成者と閲覧者の権限を厳密に分離

### NF-02: データ保護
- 引き継ぎ書はサーバーサイドに保存（作成者のみアクセス可）
- バックアップ方針はホスティング環境に依存（Phase 5で決定）

### NF-03: ユーザビリティ
- 初心者でも迷わず使える操作フロー
- エラーメッセージは原因と対処法を具体的に記述
- スマートフォン対応（レスポンシブ）

### NF-04: 可用性
- Vercelデプロイを前提（Phase 5で確定）
- データベース可用性はホスティングサービスに依存

## 5. データモデル（論理設計）

```
users
  id (UUID)
  email
  created_at

documents
  id (UUID)
  user_id (FK → users.id)
  title
  data (JSONB)        -- セクション5つのデータ全体
  version (INT)       -- 競合検知用
  created_at
  updated_at

share_tokens
  id (UUID)
  document_id (FK → documents.id)
  token (UUID)        -- 共有URL用のランダムトークン
  status              -- 'active' | 'revoked'
  expires_at          -- NULL (MVP), TIMESTAMP (v1.0以降)
  created_at
  revoked_at
```

## 10. 開発方針

- T-04〜T-06の設計成果物を最優先の仕様とする
- 技術方針は調査後に確定する（Phase 5）
- 1機能ずつ実装→テスト→確認のサイクルを守る

- コミット前に変更内容とテスト結果を確認する
- セキュリティとデータ保護を最優先で設計する
- 秘密情報をソースコードやGitに含めない
- Supabase採用時はRLSを適切に設定する
