## テスト前の準備

### 1. 開発サーバーを起動する

ターミナルで以下を実行：

```bash
cd /Users/itotaku/dev/AI_test/HikiTsugi-v2
npm run dev
```

「ready started server on 0.0.0.0:3001」と表示されたら起動完了。  
ブラウザで `http://localhost:3001` を開く。

### 2. テスト用アカウントを用意する

**既存アカウントがある場合:** そのまま使用してよい。

### 3. 競合テスト（テスト5・6）用の準備

同じパソコンで2つのブラウザタブを開いておく（例：通常ウィンドウとシークレットウィンドウ）。

## テスト1：新規登録とログイン

### 目的
ユーザーが新しいアカウントを作成し、ログインできること。

### 操作手順

**新規登録:**
1. `http://localhost:3001` を開く → `/login` にリダイレクトされることを確認
2. 「アカウント作成」リンクをクリック → `/register` が開く
3. メールアドレスとパスワード（6文字以上）を入力
4. 「アカウントを作成」ボタンをクリック
5. 「確認メールを送信しました」の画面が表示されることを確認
6. 入力したメールアドレスの受信箱を開く
7. Supabase からの確認メール内のリンクをクリック

**ログイン:**
1. `http://localhost:3001/login` を開く
2. 登録したメールアドレスとパスワードを入力
3. 「ログイン」をクリック

### 期待する結果
- ログイン後 `/dashboard` に遷移する
- 画面右上にログイン中のメールアドレスが表示される
- 「引き継ぎ書一覧」と「＋ 新規作成」ボタンが表示される

### 合格・不合格の判断
| 状態 | 判断 |
|---|---|
| `/dashboard` に遷移し、メールアドレスが表示される | **合格** |
| ログインページのまま動かない | **不合格** |
| 確認メールが届かない | **要確認**（Supabase の Auth 設定を確認） |

### 不合格時に確認するファイル
- `app/(auth)/login/page.tsx` — ログイン処理
- `app/(auth)/register/page.tsx` — 登録処理
- `proxy.ts` — 未ログイン時のリダイレクト

### スクリーンショットを撮る箇所
- ダッシュボード（右上のメールアドレスが写ること）

## テスト3：自動保存の状態表示とタイミング

### 目的
入力するたびに自動保存が動作し、画面に保存状態が表示されること。

### 事前準備
テスト2が完了し、編集画面が開いていること。

### 操作手順（保存状態の確認）
1. 「業務名を入力」の欄に何か文字を入力する（例：「テスト引き継ぎ書」）
2. 画面右上の保存状態の表示を見る：
   - 入力直後 → 「保存中...」（グレーの文字）が表示されることを確認
3. そのまま2秒ほど待つ
4. 「保存済」（緑の文字）に変わることを確認

### 操作手順（連続入力の確認）
1. 文字を素早く連続で入力する（例：「テスト引き継ぎ書12345」）
2. 入力中は「保存中...」のまま
3. 入力をやめて2秒後に「保存済」に変わることを確認（入力するたびに2秒がリセットされる）

### 保存状態の表示場所
画面の**右上**にある小さい文字：

| 表示 | 意味 |
|---|---|
| （何も表示なし） | まだ入力していない状態 |
| 保存中... | 2秒待ち中、またはサーバーに送信中 |
| 保存済 | サーバーへの保存が完了 |
| 保存失敗 — ローカルに保存済 | ネットワークエラー（内容はブラウザ内に保存済み） |
| 競合を検知 | 他のタブ・デバイスで同時編集が発生 |

### 期待する結果
- 入力後 2秒以内に「保存中...」→「保存済」の順に表示が変わる
- 連続入力中は「保存中...」が維持され、止まってから2秒後に「保存済」になる

### 合格・不合格の判断
| 状態 | 判断 |
|---|---|
| 入力後に「保存中...」→「保存済」と変わる | **合格** |
| 「保存済」に変わらずずっと「保存中...」 | **不合格** |
| 「保存失敗」が表示される | **不合格**（ネットワークかサーバーエラー） |

### 不合格時に確認するファイル
- `hooks/useAutoSave.ts` — 自動保存ロジック
- `app/api/documents/[id]/route.ts` — PATCH API（保存処理）
- DevTools > Network タブで PATCH リクエストの結果を確認

### スクリーンショットを撮る箇所
- 「保存中...」が表示されている瞬間
- 「保存済」が表示された状態

## テスト4：ネットワーク切断時の保存失敗とlocalStorageバックアップ

### 目的
ネットワークが切れても入力内容が消えず、ブラウザ内に保存されること。

### 事前準備
編集画面が開いていること。

### DevToolsの開き方（Chromeの場合）
- Macの場合：`Command + Option + I` を押す
- 「Network（ネットワーク）」タブをクリック

### 操作手順（オフラインにする）
1. DevTools の Network タブを開く
2. 「No throttling」と書かれたドロップダウンを「Offline」に変更
3. 画面上部に「オフライン」と表示されることを確認

### 操作手順（バックアップの確認）
1. オフラインの状態で「業務名」に文字を追加入力する（例：「オフラインテスト」）
2. 2秒ほど待つ
3. 画面右上に「保存失敗 — ローカルに保存済」（赤文字）が表示されることを確認
4. DevTools の「Application（アプリケーション）」タブを開く
5. 左メニューの「Storage > Local Storage > http://localhost:3001」をクリック
6. `draft-{ドキュメントID}` というキーが存在することを確認
7. その値をクリックすると、入力した文字が含まれていることを確認

### 操作手順（オンラインに戻す）
1. Network タブで「Offline」を「No throttling」に戻す
2. 追加で何か文字を入力する
3. 「保存済」に変わることを確認
4. Application タブで `draft-{ドキュメントID}` が消えることを確認

### 期待する結果
- オフライン中でも入力内容が localStorage に保存される
- 「保存失敗 — ローカルに保存済」が表示される
- オンライン復帰後の入力で正常に保存され、localStorage のデータが消える

### 合格・不合格の判断
| 状態 | 判断 |
|---|---|
| localStorage に `draft-{id}` が存在し、オンライン復帰後に消える | **合格** |
| localStorage にデータが保存されない | **不合格** |
| オンライン復帰後も保存失敗のまま | **不合格** |

### 不合格時に確認するファイル
- `hooks/useAutoSave.ts` の `triggerSave` 関数（localStorage への書き込み処理）

### スクリーンショットを撮る箇所
- 「保存失敗 — ローカルに保存済」が表示された状態
- DevTools > Application で localStorage に `draft-{id}` が表示されている状態

4. 編集していた内容（業務名など）が表示されていることを確認
5. 「閉じる」ボタンをクリックしてバナーを消す
6. オンラインの場合、少し文字を追加入力して「保存済」になることを確認

### 期待する結果
- リロード後にバナーが表示される
- バックアップされた内容が画面に復元されている

### 合格・不合格の判断
| 状態 | 判断 |
|---|---|
| バナーが表示され、内容が復元されている | **合格** |
| バナーが表示されない | **不合格** |
| 内容が復元されず空になっている | **不合格** |

### 不合格時に確認するファイル
- `components/editor/DocumentEditor.tsx` の `useEffect`（localStorage の読み込み処理）

## テスト6：複数タブでの競合検知

### 目的
2つのタブで同じドキュメントを開き、片方で保存したあとにもう片方で編集すると「競合」が検知されること。

### 事前準備
- テスト用ドキュメントが1つあること
- 2つのブラウザウィンドウ（またはタブ）を用意する

### 操作手順
1. **タブA** で編集画面（`/documents/{id}/edit`）を開く
2. **タブB** でも同じURL（同じ `{id}`）の編集画面を開く
3. **タブA** の「業務名」欄に文字を入力し、「保存済」になるまで待つ（2〜3秒）
4. **タブB** で何か文字を入力する（タブAとは別の文字を入力）
5. タブBで2秒ほど待つ

### 期待する結果
タブBの画面中央に次の**ダイアログ（ポップアップ）**が表示される：

```
競合が検知されました
他のデバイスまたは別のタブでこのドキュメントが更新されました。
どちらの内容を使用しますか？

[ サーバーの内容を読み込む ]
[ 自分の変更を上書きする ]
```

### 合格・不合格の判断
| 状態 | 判断 |
|---|---|
| 競合ダイアログが表示される | **合格** |
| ダイアログが表示されず「保存済」になってしまう | **不合格**（バージョン管理が機能していない） |
| 「保存失敗」になる（ネットワークエラーではなく） | **要確認** |

### 不合格時に確認するファイル
- `app/api/documents/[id]/route.ts` — PATCH 時の `WHERE version = ?` 部分
- `hooks/useAutoSave.ts` — 409 受信時の `setConflictInfo` 処理

### スクリーンショットを撮る箇所
- 競合ダイアログが表示されたタブBの画面

## テスト7：競合の解消

### 目的
競合ダイアログで「サーバーの内容を採用」または「自分の内容で上書き」が正常に動作すること。

### 事前準備
テスト6を実施し、タブBに競合ダイアログが表示されている状態。

### 操作手順A：サーバーの内容を採用する

1. 競合ダイアログの「サーバーの内容を読み込む」ボタンをクリック
2. ページが自動的にリロードされることを確認
3. タブAで保存した内容（タブAの業務名）が表示されていることを確認
4. 競合ダイアログが消えていることを確認

### 操作手順B：自分の変更で上書きする（別途テスト）

1. もう一度テスト6を繰り返して競合ダイアログを出す
2. 「自分の変更を上書きする」ボタンをクリック
3. ダイアログが消えることを確認
4. しばらくして「保存済」と表示されることを確認
5. タブAをリロード → タブBで入力した内容になっていることを確認

### 期待する結果
- Aの操作: タブAの内容でページが更新される
- Bの操作: タブBの内容がサーバーに保存され、タブAにも反映される

### 合格・不合格の判断
| 状態 | 判断 |
|---|---|
| 選んだ内容が正しく反映される | **合格** |
| ボタンを押してもダイアログが消えない | **不合格** |
| 上書き後も「競合を検知」が繰り返す | **不合格**（デバウンスが止まっていない） |

### 不合格時に確認するファイル
- `hooks/useAutoSave.ts` の `resolveConflict` 関数
- `components/editor/DocumentEditor.tsx` の競合ダイアログ部分

### スクリーンショットを撮る箇所
- 競合解消後の編集画面（正しい内容が表示されている状態）

## テスト11：共有URLの失効

### 目的
「共有を停止」したあと、以前の共有URLにアクセスできなくなること。

### 事前準備
テスト9・10が完了し、共有URL（コピー済み）があること。

### 操作手順（失効させる）
1. ログイン済みのブラウザで共有管理ページ（`/documents/{id}/share`）を開く
2. 「共有を停止」ボタンをクリック
3. 「停止済み」（グレーのラベル）に変わることを確認

### 操作手順（失効を確認する）
1. シークレットウィンドウを開く
2. コピーしておいた共有URL（`http://localhost:3001/view/...`）にアクセス
3. 以下を確認：
   - 「共有が停止されました」というエラーメッセージが表示される
   - 「トップページへ」リンクが表示される
   - ドキュメントの内容が**表示されない**こと

### 操作手順（再発行できるか確認）
1. 共有管理ページで「新しい共有URLを発行」をクリック
2. 新しいURLが発行されることを確認（以前のURLとは異なること）

### 期待する結果
- 失効後は `/error?reason=revoked` にリダイレクトされ「共有が停止されました」が表示される
- 再発行すると新しいURLが生成される

### 合格・不合格の判断
| 状態 | 判断 |
|---|---|
| 失効後に「共有が停止されました」が表示される | **合格** |
| 失効後もドキュメントが表示されてしまう | **不合格** |

### 不合格時に確認するファイル
- `app/api/documents/[id]/share/route.ts` — DELETE 処理
- `app/view/[token]/page.tsx` — status チェック
- `app/error/page.tsx` — エラーメッセージ表示

### スクリーンショットを撮る箇所
- 「共有が停止されました」エラー画面

## テスト12：エラー画面の表示

### 目的
無効または失効したトークンにアクセスしたとき、適切なエラー画面が表示されること。

### 事前準備
開発サーバーが起動していること。

### 操作手順A：無効なトークン
1. ブラウザで `http://localhost:3001/view/aaaaabbbbbcccccdddddeeeeefffff00` にアクセス
   （でたらめな64文字の文字列）
2. 表示を確認

### 操作手順B：失効済みトークン
テスト11の「失効を確認する」手順で確認済みのはず。

### 期待する結果

| アクセス内容 | 期待するメッセージ |
|---|---|
| 存在しないトークン | 「このURLは有効ではありません」 |
| 失効済みトークン | 「共有が停止されました」 |

どちらも「トップページへ」リンクが表示される。

### 合格・不合格の判断
| 状態 | 判断 |
|---|---|
| それぞれのメッセージが正しく表示される | **合格** |
| 503/500 などのサーバーエラーが表示される | **不合格** |

### 不合格時に確認するファイル
- `app/view/[token]/page.tsx` — エラーリダイレクト処理
- `app/error/page.tsx` — メッセージ定義

### スクリーンショットを撮る箇所
- 「このURLは有効ではありません」エラー画面
